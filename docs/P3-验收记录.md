## 二、实测数据

### 2.1 R1:路书导出套件

- **高差图**:`core/export/profileGraphic.ts`——SVG 字符串生成与 PNG 画布绘制分离成 model/render 两层,PNG 固定 `DEFAULT_PNG_SCALE = 4`(4× 分辨率,供粘贴进文档)。18 + 11 = 29 个单测覆盖坐标换算、刻度、多边形填充路径。
- **Excel 路书**:`core/export/excelRouteBook.ts`——两个 Sheet(全程概述 + 节点明细),数字全部来自既有的 `computeSegments`/`estimateArrivals`/`alignCutoffsToSegments`,不重新发明一套判断规则(红黄绿状态色直接取自 `RouteBookData`,而不是在 Excel 层重新判断阈值)。`generateRouteBookWorkbook` 有一个**真实 ExcelJS 往返测试**:生成 `.xlsx` Blob 后用 ExcelJS 本身重新读回,断言 Sheet 名、表头、嵌入的高差图 PNG 都在——这比只测"纯函数返回的模型对象"更接近真实产物。ExcelJS(压缩后 929.58 kB)通过动态 `import()`,构建产物里独立成 `exceljs.min-*.js` chunk(见 2.4),不进主包,和 Cesium 的处理方式完全一致。
- **配速卡**:`core/export/paceCard.ts`——`DEFAULT_CARD_DIMENSIONS_MM = { widthMm: 180, heightMm: 60 }`,180mm 对应成年人前臂周长(220~280mm)绕一圈可贴合,60mm 按"跑动中瞥一眼要看清"折算约 6 行 9~10pt 等宽字体。20 个单测。
- **共用数据层**:`core/export/routeBookData.ts` 把三个导出物要用的行数据(含累计里程/爬升/下降)统一算一次,10 个单测;三者不会因为各自独立实现前缀和而对不上数字。
- **本节合计**:67 个单测(5 个文件),全部通过。

### 2.2 R2:CP 实景照片 + EXIF GPS 锚定

- **EXIF 解析器**:`core/photo/exif.ts`——手写 TIFF/IFD 解析器,只读 GPS 经纬度、`DateTimeOriginal`、`Orientation` 三个字段,**没有新增任何依赖**(调研过 exifr/exif-js/piexifjs,决定不引入)。15 个单测用手写字节数组构造合成 JPEG(不提交二进制 fixture,保持"改动能被看懂"),覆盖四个半球符号处理、DMS→十进制换算、EXIF/GPS 缺失、数据截断等分支。
- **锚定阈值**:`core/pipeline/photoAnchor.ts`——`PHOTO_ANCHOR_MAX_DISTANCE_M = 150`(超过 150m 拒绝锚定,视为"这张照片明显不在这条轨迹附近"),`PHOTO_MERGE_DISTANCE_M = 50`(50m 内的照片与已有 CP 合并,不重复创建检查点)。10 个单测。
- **降级/隐私处理**:`core/photo/downscale.ts` 把原图缩到长边 ≤1440px(`MAX_DIMENSION_PX`)、JPEG 质量 0.82 重新编码,副作用是原图的 EXIF(含 GPS/时间)在重新编码后天然不随缩略图带出——这是刻意依赖的行为,不是巧合。**这一步依赖 `createImageBitmap`/`<canvas>`,无法在 Node 环境单测**,是本里程碑里少数结构性缺少单测覆盖的环节,需要真人在浏览器里选一张真实带 GPS 的手机照片验证"缩放、摆正方向、EXIF 清除"三件事同时生效。
- **本节合计**:28 个单测(2 个文件),全部通过;`downscale.ts`/`attachPhoto.ts`/`CpPanel.tsx` 的照片上传交互本身未经真人验证。

### 2.3 R3:镜头模板库 + 关键帧编辑器

- **模板库**:`cesium/cameraTemplates.ts`——`CAMERA_TEMPLATES` 数组含 4 套模板(`gods-eye-opening` 上帝视角开场、`fast-flyover` 快速掠过、`climb-slowdown` 爬坡减速、`finish-orbit` 终点环绕),达到方案「≥4 套模板」的验收线。16 个单测。
- **关键帧轨道**:`cesium/keyframes.ts`——按里程键控(mileage-keyed)的关键帧数组,`distanceBehindM`/`heightAboveM`/`pitchDeg`/`headingOffsetDeg`/`fovDeg`/`speedMultiplier` 均用 smoothstep(而非线性)插值。24 个单测。
- **一条共用的相机解析路径**:实时预览(`cesium/flythrough.ts` 的 `FlythroughEngine`)与确定性导出(`cesium/frameExport.ts`)**都不各自维护一份相机计算逻辑**——`frameExport.ts` 直接驱动同一个 `FlythroughEngine` 实例逐帧步进,而 `FlythroughEngine` 内部两处(实时相机更新、`speedMultiplier` 读取)都调用同一个 `sampleCameraAt(this.cameraTrack, this.mileageM)`,详见 `flythrough.ts:490`/`543`。这正是方案要求的"不为导出单独发明一套相机数学"。
- **本节合计**:43 个单测(2 个文件);`ui/KeyframeEditor.tsx`(拖拽编辑关键帧)、`ui/FlyView.tsx` 里模板选择与实际相机运动的联动,均需要 Cesium 渲染帧,本环境无法验证,与 P1/P2 记录里 R3 一样的性质的项一并标注在此。

### 2.4 R4:自包含交互网页导出

- **数据裁剪**:`core/export/webPage.ts`——`DEFAULT_MAX_POINTS = 4000`,超过则抽稀,始终保留首尾点;`includePhotos: false` 时整段剥离 `photoUrl`,不进入 payload。
- **地图实现**:内嵌一段手写 Canvas 2D 绘图代码,叠加 `map/basemapStyle.ts` 已在用的同一套 OSM 光栅瓦片 URL 模板/署名(`OSM_TILE_URL_TEMPLATE`/`OSM_ATTRIBUTION`),不引入任何第三方地图 JS 库。页面自身的 JS/CSS/字体**全部内联在单一 HTML 文件里**,没有对 CDN 或任何外部脚本/样式表/字体的引用(全文唯一的 `http://` 字符串是 SVG 命名空间 URI,不是网络请求);地图瓦片图片本身仍需要打开页面时联网向 OSM 拉取,这是"自包含单文件"与"离线可用"两个不同要求里,本交付物只承诺前者、方案原文也只要求前者的地方。
- **本次会话对真实速攀129轨迹(5,038 点,3 个 CP)的实测**:解析原始 GPX → `buildWebPagePayload`(按 4000 点上限抽稀)→ `renderWebPageHtml` → 实测 HTML 体积 **438.6 KiB**,与 milestone 交接材料里记录的 437.7 KiB 基本一致(差值来自本次复测用的 CP 坐标/名称与原始记录不完全相同,不是代码回归)。
  - 该测量脚本为临时验证脚本,未提交进仓库(仓库自带的 `tests/core/export/webPage.test.ts` 用等距合成轨迹复现同一量级的体积,当前合成 5,038 点的测量结果为 439.7 KiB,量级一致)。
- **体积透明度(P3-R5 commit 1,已在本里程碑内修复)**:`computeWebPageSizeBreakdown` 区分"照片撑大的体积"与"路线数据本身撑大的体积",`ExportPanel.tsx` 据此展示不同文案(而不是笼统一句"文件较大"),修复了此前照片批量导入和路线抽稀预警会共用同一句提示语、用户看不出超限原因是照片还是路线的问题。
- **本节合计**:30 个单测,全部通过;页面在真实浏览器里的可用性(地图交互、缩放、CP 点击、离线/弱网下瓦片加载失败的观感)未经真人确认。

### 2.5 R5:传感器覆盖度摘要 + 行动建议

- **传感器覆盖度**(commit 2,`a7ac9e1`):`core/perf/sensorCoverage.ts` 独立统计 hr/cadence/power/temperature 四列的存在性、覆盖率、有效读数的 min/max/mean,`present:false`(整列没有)与 `present:true, coverage:0`(列在,但每个点都是缺失哨兵)刻意区分,不合并成同一种"没有数据"。9 个单测;`PerformancePanel.tsx` 已有的「传感器覆盖」表格直接消费这个结果。
- **行动建议**(commit 3,本次会话完成的工作):`core/perf/insights.ts` 从已经算好的分段配速/GAP、爬坡分段、传感器覆盖率、CP 关门余量里筛出"值得单独说一句"的模式,固定顺序输出。5 类洞察及其命名阈值:

  | 洞察 | 触发条件 | 命名阈值 |
  |---|---|---|
  | `late_pace_decay` 后半程配速衰减 | 前三分之一 vs 后三分之一平均 GAP,后段慢出的比例 ≥ 阈值 | `LATE_PACE_DECAY_THRESHOLD_PCT = 15`(%),另需总分段数 ≥6、每个三分之一至少 2 个可比样本 |
  | `costliest_climb` 最费时爬坡 | 某段爬坡"耗时占比/距离占比"的比值 ≥ 阈值 | `COSTLIEST_CLIMB_RATIO_THRESHOLD = 1.5`,另需该段距离占比 ≥ `COSTLIEST_CLIMB_MIN_DISTANCE_SHARE = 0.03`(3%) |
  | `cutoff_margin_missed` / `cutoff_margin_thin` | 实际到达时间晚于关门(missed)/ 余量 < 阈值(thin) | `THIN_CUTOFF_MARGIN_SEC = 1200`(20 分钟,复用 `pace/models.ts#estimateArrivals` 自己的绝对下限,保持两处口径一致) |
  | `split_anomaly_slow` / `split_anomaly_fast` | 单公里配速偏离全程平均配速的比例 ≥ 阈值 | `SPLIT_ANOMALY_PCT = 30`(%),另需 ≥5 个可比整公里分段,并排除 <500m 的收尾短分段 |
  | `sensor_gap` | 某传感器列存在但覆盖率 < 阈值 | `SENSOR_GAP_COVERAGE_THRESHOLD = 0.5`(50%) |

  **每条洞察的文案里都直接写入触发它的具体数字**(如"前段…平均 GAP 5:00/km，后段…5:45/km，慢了 15%"),`evidence` 字段把同一批数字结构化保留一份,供测试核对文案里的数字确实来自输入而不是拼出来的。没有任何一条阈值命中时,`deriveInsights` 返回空数组——`PerformancePanel.tsx` 对应展示「本次数据未发现值得单独指出的模式」,不会硬凑一条空话填满这一节。这正是 P3 方案自己在风险登记表里点名的 R-4(「行动建议容易沦为套话」),应对方式写的就是"只在数据支持时给出结论,并附依据数值;宁可不给,不给空话"——本记录核对过 `insights.ts` 的每一个探测函数,确认这条纪律被严格遵守(见下节"对既有模块的复核")。
- **UI wiring**:`PerformancePanel.tsx` 在「深度分析」之后新增「行动建议」区块,通过与其它区块相同的 `perfAvailability`/`resolveTrackKind` 门禁——只对 `recorded` 轨迹渲染,规划路线不会看到这一节(规划路线没有"跑得怎么样"可言)。
- **本节合计**:55 个单测(9 + 46),全部通过。

### 2.6 对既有模块的复核(`core/perf/insights.ts`,commit 2 已写好、本次会话补测试与 UI 之前的复核)

进入本里程碑时,`insights.ts` 已经写好但未接入任何调用方、无测试。复核结论:**该文件的证据约束在代码层面已经如实遵守**——

- 5 个探测函数都在对应数字未达到命名阈值时返回 `undefined`/`[]`,不产出任何一条"没有依据的建议";
- 每条 `Insight.text` 引用的数字都能在其 `evidence` 字段里找到同一个数(本次新增的 46 个测试逐一核对了这一点,包括跨越浮点误差的边界值,如 15%/1.5×/30%/50%/1200s 五个阈值各自的"恰好命中"与"刚好不命中"两侧);
- `deriveInsightsForTrack`(面向 `Track` 的入口)在内部又做了一层防御性门禁(`analysis.applicable` 为假时直接返回空数组),即便调用方忘记先检查 `recorded` 也不会算出假建议。

复核过程中**未发现需要修复的缺陷**——文件头部的文档注释(§硬性要求 1~4)与实际实现完全一致,是本次少见的"文档即代码承诺,且代码兑现了承诺"的模块。

## 四、缺口与后续动作

1. **R3 渲染画面本身未经真人验证**——模板/关键帧的插值数学、`sampleCameraAt` 共享路径均有单测,但"选一个模板、拖一个关键帧、实际出片"这个完整流程需要真实 Cesium 渲染帧,本环境结构性无法提供,需用户在自己的浏览器里走一遍。
2. **R2 的照片上传/缩放/摆正管线未经真人验证**——`downscale.ts` 依赖 `createImageBitmap`/`<canvas>`,无法在 Node 环境单测;需要用户实际选一张带 GPS EXIF 的手机照片,确认锚定位置、缩放画质、方向摆正、EXIF 清除四件事同时正确。
3. **R4 导出页面的真实浏览器可用性未经真人验证**——地图 Canvas 交互(缩放、拖动、CP 点选)、OSM 瓦片在弱网/离线下的实际观感,均需要打开导出的 HTML 文件实测,构建产物/单测只能证明"文件体积和数据结构正确"。
4. **R1 的 Excel/WPS/Google Sheets 兼容性未经真人验证**——`generateRouteBookWorkbook` 已经过 ExcelJS 自身的往返读取校验,证明写出的是一份结构合法的 `.xlsx`,但"在真实 Excel/WPS/Google Sheets 里打开是否样式不丢失"这条验收标准本身要求的是三个具体第三方应用的渲染结果,需要真人在这些应用里实际打开确认。

## 五、已知限制(设计取舍,非缺陷)

以下三条延续自代码里已经写明的文档注释,本记录如实转述,不重新措辞淡化:

- **R3 的关键帧 `speedMultiplier` 只对实时预览生效,确定性导出保持恒定速度**:`cesium/flythrough.ts` 的实时更新路径读取 `sampleCameraAt(...).speedMultiplier` 来调整巡游速度,但确定性导出(`frameExport.ts`)按固定帧率/固定里程步长逐帧渲染,不应用这个倍速——效果是:关键帧在**每个里程点上的取景**(距离、高度、俯仰角、视场角)在实时预览和最终导出的视频里完全一致,但如果关键帧设计了"经过一段爬坡时放慢镜头"的节奏,这个节奏本身只体现在实时预览里,最终导出的 MP4 里这段路程仍然按恒定速度经过。
- **轨迹经过工具箱操作(反转/抽稀/简化等)后,关键帧不会重新按新的里程/点序调整**:`core/model/track.ts` 的 `cameraTrack` 字段和其它 `meta` 字段一样,被 `core/toolbox/ops.ts` 的每个操作原样携带(`{ ...src.meta, ... }`),但里程锚点不会跟着新的点序重新映射——反转一条已经编排好关键帧的轨迹后,关键帧的里程锚点会明显错位(例如原本锚在"3km 处开始减速"的关键帧,反转后仍然锚在里程 3km,但那已经是轨迹上完全不同的一段路)。
- **R4 内嵌的检查点照片没有自己的体积上限**:`webPage.ts` 的 `includePhotos` 只是"要不要带上"的开关,不对单张照片或总照片体积做任何裁剪/拒绝;体积透明度(`computeWebPageSizeBreakdown`,commit 1)只负责**告诉用户**照片占了多少体积,不负责限制它。真正的体积上限来自更早一层——`core/photo/downscale.ts` 把原图缩到 ≤1440px/JPEG 质量 0.82 后通常几十到几百 KB——但如果一条轨迹挂了几十个 CP、每个都有照片,导出页面的体积仍然可能变得很大,且没有任何环节会拒绝或警告"这次导出可能过大"到 R4 自己的产物层面。

## 七、结论

P3 的五个里程碑(R1~R5)在代码/单测/构建层面全部完成,累计新增/覆盖 223 个单测(67+28+43+30+55),`npx tsc -b --force`(strict)与 `npm run build` 均无错误,主包体积 1,347.47 kB,较里程碑开工前的约 1,338 kB 仅增加约 9.5 kB。R1(路书套件)、R2(EXIF 照片锚定)、R4(自包含网页)三个"纯生成类"里程碑均有单测 + 真实产物往返验证(ExcelJS 读回、真实速攀129轨迹导出实测 438.6 KiB)支撑;R5(传感器覆盖 + 行动建议)新增的 `insights.ts` 经本次复核确认严格遵守"每条建议必须引用真实测量数字、没有证据就不输出"的硬性要求,未发现编造数据的缺陷。
