## 结论摘要

TrailCraft **不是原型项目**，而是一套已有明确产品边界、领域分层和高测试覆盖的越野跑路线工作台。它当前以纯前端本地应用形态实现了轨迹导入与处理、二维地图规划、三维巡游、赛前路书导出、表现评估等能力。最适合 Manus 的第一步并非推倒重写，而是以现有 `src/core` 领域逻辑为资产，迁移为可发布的 Web 应用，并先把“稳定的路线工作台”作为上线范围；云端协作、赛事库、公开分享等应作为经产品确认后的第二阶段能力。[1]

> **建议的发布口径：** 先上线一个“本地优先、可在浏览器中完成 GPX/FIT/KML 导入、路线分析和路书输出”的 TrailCraft Web 版；三维巡游和视频导出仅在经过目标浏览器与真实网络的人工验收后标记为正式支持。

| 中国网络与地图合规 | 待确认 | 需在真实目标网络检查地图/地形性能，并在商业发布前完成测绘、底图许可和隐私合规评估。[1] |

## 1. 当前产品能力

TrailCraft 面向越野跑者与赛事组织者，将一条轨迹转化为赛前路线计划、路书和三维传播内容。README 中明确其当前定位为“纯前端本地应用”：轨迹保存在浏览器 IndexedDB 与本地文件内，不需要账号、后端或服务器。[1]

| 工作流 | 已实现能力 | 审查判断 |
| --- | --- | --- |
| 导入与存档 | GPX、KML、FIT 导入；Web Worker 解析；WGS-84/GCJ-02/BD-09 识别转换；浏览器本地存档与 JSON 工程备份。 | 适合保留为第一版核心，隐私边界清楚。 |
| 二维规划 | MapLibre 地图、高程剖面、轨迹分割/拼接/反向/清洗/抽稀、手绘路线、撤销/重做、CP 节点与配速预警。 | 核心用户价值完整，优先验收并迁移。 |
| 三维巡游 | Cesium 地形/影像、镜头模板、里程键控关键帧、等高线、距离雷达、WebCodecs H.264 导出和降级 MediaRecorder。 | 差异化显著，但属于高 WebGL/浏览器兼容性风险模块。 |
| 表现分析 | 实跑/规划判断、ITRA 风格逆向表现分、速算、传感器覆盖概览与证据驱动建议。 | 适合继续保留，但必须清楚标示其不是官方 ITRA 积分。 |
| 输出 | Excel 路书、高差图 SVG/PNG、腕带配速卡、自包含交互网页、GPX 导出。 | 与赛前实际场景契合，是最适合优先上线验证的高价值能力。 |

应用主界面采用“数据 / 规划 / 分析 / 输出 / 视图”的任务分组，中心地图舞台加底部高程剖面，已具备专业工作台的交互骨架。[4]

## 2. 代码与质量证据

代码库当前包含 **135 个 TypeScript/TSX 源文件、约 24,191 行源代码、82 个测试文件、约 12,340 行测试代码和 15 份文档**。`src/core` 被刻意设计为无框架依赖的纯 TypeScript 领域层，涵盖解析、坐标系、测地距离、轨迹工具箱、统计、配速、表现评分、导出、照片与工程模型；这是后续迁移时最值得保持稳定的资产。[1]

## 3. Manus 中的迁移判断

已创建一个 Manus 静态 Web 项目作为迁移验证容器。其模板提供 React 19、Tailwind 4、Wouter、组件库与发布工作流。现有 TrailCraft 同样为 React + TypeScript + Vite 前端，因此**领域逻辑迁移的结构匹配度很高**；但现有地图与三维视图需要单独的技术验证，不应把“能构建”误写成“已可稳定上线”。

对于视觉迁移，已确定“**山脊工作台**”方向：地图为主舞台，功能按任务而非零散面板组织，玄武岩暗色背景配山径橙高亮，数值使用等宽字体，保留路线工作台的专业感。该方向已经记录在项目的 `ideas.md` 中，并已准备专用品牌标记、山脊主视觉、等高线纹理和三维巡游视觉资产。

### 3.1 推荐的分层迁移顺序

| 阶段 | 范围 | 目标 | 发布判断 |
| --- | --- | --- | --- |
| A：可发布核心 | 导入、轨迹列表、二维路线编辑、高程剖面、CP、配速/关门、工程本地保存、基础导出。 | 先交付日常可用的“赛前路线工作台”。 | 达到浏览器与移动端核心流程验收即可发布。 |
| B：可靠分析与导出 | 表现分析、Excel/高差图/配速卡/交互网页输出，明确非官方积分与本地数据边界。 | 把可带去比赛的成果做扎实。 | 验收真实文件在 WPS、Excel、Google Sheets 与移动端下载流程。 |
| C：三维传播工作室 | 三维巡游、镜头模板、关键帧、等高线、雷达、视频导出。 | 将差异化能力变为可陈述、可演示的产品功能。 | 只在完整设备矩阵和真实样例验证通过后上线为正式特性。 |
| D：云端产品化（可选） | 登录、项目同步、照片/文件存储、分享链接、赛事库、多活动对比、个人路网。 | 从本地工具升级为协作/服务型产品。 | 需要单独确认隐私、成本、账号体系、数据保留和运营策略。 |

### 3.2 架构选择，需要您确认

| 方案 | 描述 | 优点 | 代价与适用场景 |
| --- | --- | --- | --- |
| **方案 1：本地优先静态版（建议先选）** | 发布为浏览器内处理的个人/赛事路线工具，轨迹与照片默认留在用户设备。 | 最贴近现有代码与隐私承诺；迁移风险最低；可较快获得真实用户反馈。 | 不具备跨设备同步、分享链接、多人协作或赛事运营后台。 |
| 方案 2：本地优先 + 可选云备份 | 默认本地处理；用户登录后可手动备份工程、照片和导出物。 | 延续隐私定位，同时解决换设备和数据丢失。 | 需要身份、文件存储、数据权限、删除策略与隐私声明。 |
| 方案 3：赛事协作平台 | 赛事方管理路线、CP、路书和对外发布；跑者查看、复制与提交记录。 | 产品天花板更高，适合赛事组织方。 | 已不是简单迁移：需要角色权限、数据模型、审核、内容运营、地图许可和长期维护。 |

## 4. 下一轮最有价值的补充材料

现在并不需要更多泛泛的素材。若要在下一轮把架构、范围和上线节奏定下来，下列信息最有价值。

| 所需信息 | 为什么需要 | 可接受形式 |
| --- | --- | --- |
| 首发目标用户与首要场景 | 决定优先本地工具、跑者个人版还是赛事协作版。 | 一句话选择，例如“国内越野跑者赛前自用”。 |
| 首发地域与平台 | 影响底图、地形、合规、语言和性能验收。 | 例如“中国大陆 Web 优先，桌面 Chrome 优先”。 |
| 三维视频是否是首发刚需 | 决定是否将 C 阶段阻塞首发，或以 Beta 标记。 | “必须首发 / 可 Beta / 后续再做”。 |
| 是否允许登录、云同步和分享 | 决定是否保持静态项目，还是升级为带数据库、用户与文件存储的完整应用。 | 对“账号、工程云备份、公开分享”分别回答是/否。 |
| 真实验收素材 | 验证解析、地图、配速、CP、导出和视频。 | 3–5 条脱敏 GPX/FIT/KML；一条有 CP 的赛事路线；如有，1–3 张含 EXIF GPS 的照片。 |

## 5. 推荐的下一步决策

建议先确定以下四项，然后再开始迁移代码：

1. **首发选择方案 1、2 还是 3。**
2. **首发是否必须包含三维巡游与 MP4 导出。**
3. **首发地域与目标设备组合。**
4. **是否提供 3–5 条可用于验收的脱敏真实轨迹。**

在您确认后，我会将 Manus 项目从迁移验证容器推进为对应版本：先建立产品骨架和数据模型，再按上表的 A→B→C 或云端路径实施，并在创建发布检查点后由您在界面中点击 Publish 完成上线。
