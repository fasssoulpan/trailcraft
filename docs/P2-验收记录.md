### 2.2 表现分析引擎:校准的诚实边界(交付物 2)

当前(2026-08-14,`src/core/perf/score.ts`)模型常数:

```
PI = min(1000, round(C × (kme_v2/hours)^K × (kme_v2/KME_REF)^M × envFactor))
C = 77.9, K = 0.850, M = 0.155, KME_REF = 270
```

`M/K = 0.155/0.850 ≈ 0.182`,对应隐含的 Riegel 耐力指数 `r = 1 + M/K ≈ 1.18`,落在超马文献引用的 `1.10~1.20` 区间内(P2 §3.2 commit 4 的约束,防止模型对长短距离的配速衰减假设脱离生理常识)。

**这组常数经过四次重新拟合**(`score.ts` 文件头注释逐次记录):
1. commit 2:加入长度归一化项(`M=0.38`),修正短距离系统性跑赢长距离的原始 2 参数模型缺陷;
2. commit 3:引入 2025 UTMB 系列国际精英成绩,重新求解 `(K,M)`,但短距离(OCC 冠军 Jim Walmsley)仍偏低分;
3. commit 4(即当前所在的"P2 Q2 commit 4"叙事):用 Riegel 耐力指数把 `M/K` 约束在生理可信区间内搜索;
4. **commit 5(2026-08-14,提交 `77c1922`,即本次会话之前刚完成)**:剔除崇礼168 100/70/50km 三行未经验证的估算数据后重新拟合,landed 在当前的 `C=77.9, K=0.850, M=0.155`。

**必须直接说明的假设与局限(不做话术淡化)**:

- **没有任何一行校准数据背后有官方发布的 ITRA 分数**。整张校准表(`src/core/perf/calibration.ts`)里只有 1 行(cyber-trail-hud 参考实现自己文档化的"平路锚点":92km/186m D+/12.75h → PI≈366)是真正独立发布的数值目标;其余全部行(2026 崇礼168 五个分组冠军、2025 UTMB 系列六场国际赛事结果、TrailCraft 自己的 12 条真实记录)只作为"结构性约束"参与拟合(例如"冠军级选手不应逼近 1000 分上限""13.9km 记录不应跑赢 167.7km 记录"),不是数值回归目标。
- **"国际精英选手校准区间落在 900~960 分"这一说法,是关于该人群竞技水平的一个推断,不是已发布的数据**——没有任何官方 ITRA 分数证实这个区间,它只是 commit 3 阶段搜索安全上限 T 时选用的一个假设起点。
- **崇礼168 的 100km/70km/50km 三行已被排除出拟合与全部结构性校验**(`calibration.ts` 的 `excludeFromFit: true`),原因:这三行的爬升数据是从 168km 赛道按比例估算的,不是实测/官方数据;其中 **70km 组冠军隐含平均时速 15.5 km/h**(约 3000m 爬升的山地赛道),快于 2025 UTMB、OCC 冠军在可比地形上的表现,物理上不可信。这一行此前(commit 3)曾经"绑架"了整个拟合,把 UTMB 冠军的分数压到低于一场区域性 70km 赛事冠军的地步。
- 结论:表现分是**社区逆向估算,不是官方 ITRA 认证分数**(方案 V2.1 §5 已明确要求界面标注这一点),`ui/PerformancePanel.tsx` 需要保留这一标注——本次会话未改动面板文案本身,仅确认其数值来源链路(`computePerformance` → P0 `computeGainLoss` 同一套滞回算法,不存在第二套爬升口径)。

- `npx tsc -b --force` 零错误(strict 模式);
- 纯逻辑单测全部通过:
  - `cesium/exportResolutions.ts` 的画幅/分辨率表、`resolutionKeysForRatio` 分组逻辑;
  - `overlay/captureLayout.ts` 竖屏/横屏/方形三种朝向在全部 5 个预设分辨率下的"不重叠、不出画布"断言(`tests/overlay/captureLayout.test.ts`);
  - `overlay/exportCredits.ts` 的署名文案组合(全部 terrain×imagery×basemapStyle 组合、含 flat-ellipsoid 兜底、含"从不虚构 OSM/Copernicus 署名"的显式断言);
  - `overlay/creditsLayout.ts`/`creditsDraw.ts` 的缩放与绘制调用(假 ctx 断言,同 `captureDraw.test.ts` 的既有约定);
- 构建产物确认主包体积、懒加载 chunk 边界均达标(见 2.4)。

**用户需在自己的机器(真实 Chrome/Edge)上确认的清单**(Q5 新增,均建立在 Q4 已验证的管线之上):

1. **多画幅实际渲染**:分别选择 16:9(1080p/4K)、9:16、1:1、3:4 四种画幅导出,确认输出的 MP4 文件本身就是该宽高比,画面内容是 Cesium 场景在该宽高比下的**原生渲染结果**,不是把 16:9 画面拉伸/裁切出来的——这是本里程碑commit 1 的核心技术改动(让 `viewer.canvas` 自身按目标宽高比渲染),已通过阅读已安装 Cesium 源码(`node_modules/cesium/Build/CesiumUnminified/Cesium.js` 的 `configureCanvasSize`/`configureCameraFrustum`/`Viewer.prototype.resize`)验证了其原理必然生效,但**没有真人看过实际输出的画面**;
2. **竖屏独立排版的实际观感**:确认 9:16/3:4 画幅里 HUD 横幅、检查点卡片、雷达是否清晰可读、位置是否符合直觉(单测只验证了矩形不重叠/不出画布,不代表视觉上"好看"或"信息层级清楚");
3. **合规片尾的实际画面**:确认片尾 3 秒黑底白字卡片是否清晰可读、居中是否准确、字体大小是否在每种画幅下都合适,以及署名文字内容是否与实际使用的地形/影像服务一致(可对照 `fly-view__badge` 角标当时显示的"地形:XX · 影像:XX"核对);
4. 导出耗时是否因为片尾追加的 90 帧(3 秒×30fps)而有可观察的额外等待,以及取消操作在片尾阶段是否仍然及时响应。

## 四、缺口与后续动作

1. **爬坡段"标注在 3D 场景"未实现**(交付物 4 验收标准的后半句):`core/perf/climbs.ts` 已能识别爬坡段并给出坡度分布,`ui/PerformancePanel.tsx` 已能展示,但把识别出的爬坡段标注到 Cesium 3D 场景(例如轨迹线分段变色、场景内标签)这部分工作本次会话未做,方案原文本身对"标注在 3D 场景"的具体形式也未展开,留待后续里程碑明确需求后实现。
2. **多画幅/合规片尾的画面本身未经真人验证**,详见第三节清单——这是本记录最大的、必须如实标注的缺口,不应被"单测全绿"掩盖。
3. **MediaRecorder 降级路径没有合规片尾**:`frameExport.ts` 的设计说明里已注明这是有意的范围收窄(降级路径没有帧序号编码器可续接,且该路径本身已永久标注"预览级",不是本交付物瞄准的"成片"),但如果后续认为降级路径也需要署名信息(哪怕只是静态水印),需要单独立项。
4. **署名片尾只覆盖地形/影像**,不覆盖轨迹数据本身的来源(用户自己上传的 GPX/FIT/KML)——这是合理的,因为轨迹数据从未对外分发合规问题,片尾要解决的是"渲染画面里出现的第三方地图数据版权"问题。
5. **背景音乐提示**:片尾固定包含"背景音乐未内置,如需公开发布请自行添加已获授权的音乐"一行,但导出的 MP4 本身当前不含任何音轨(P1/Q4 均未涉及音频管线)——这一提示只是诚实告知,不代表应用做了任何音频相关处理,后续如果要支持用户上传背景音乐需另立里程碑。

## 五、已知限制(设计取舍,非缺陷)

- **表现分是社区逆向估算,不是官方 ITRA 分数**,且当前校准存在第二节 2.2 列出的具体假设(依赖单一发布锚点、崇礼168 三行已排除、"国际精英 900~960"是推断非数据)——这不是本里程碑引入的新限制,但 Q5 验收记录有责任把它写清楚,不能让"表现分看起来是一个精确数字"掩盖其估算性质。
- **1:1 方形画幅沿用横屏(角落式)排版,不是独立的第三套模板**:`captureLayout.ts` 把方形归入"横屏"分支(`width >= height`),理由是 1080×1080 仍有足够宽度让三个角落元素不显拥挤,不同于 9:16/3:4 真正狭窄的竖屏——这是一个经过说明的设计取舍,记录在 `captureLayout.ts` 文件注释与本记录第三节,而非遗漏。
- **合规片尾固定 3 秒**,不随视频总时长或画幅调整;超短片段(例如几秒钟的巡游)片尾占比会显得偏长,但方案本身只要求"用户导出即合规",没有对时长比例提出要求。
- **降级路径(MediaRecorder/WebM)沿用 P1 的"预览级"定位不变**,详见 P1 验收记录"已知限制"一节,Q5 未改变这一点。
