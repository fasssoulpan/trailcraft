## 二、优先级与理由

按「价值 ÷ 风险」排序,而非按方案原文顺序。

### P3-A 路书导出套件(#2 #3 #4)—— 最先做

**理由**:这是选手真正带去比赛的东西。方案把关门预警称作「选手赛前功课的核心刚需」,而路书/配速卡正是那份功课的**成品形态**——现在算得出来,却带不走。

三项同源(都从已有的分段统计与配速模型生成),共用一套数据,一次做完最省。且全部是纯生成 + 下载,**不依赖浏览器渲染验证**,这在当前"渲染类功能难以验证"的处境下价值很高。

### P3-B CP 实景照片 + EXIF(#1)

**理由**:P0 就承诺的功能,欠得最久;且是 #7 照片故事视频的前置。EXIF GPS 可自动把照片锚到轨迹对应位置,这是"路书"之外另一个让路线变具体的东西。

注意合规:EXIF 含拍摄位置与时间,属个人信息,处理必须全程本地、不上传。

### P3-C 镜头模板库 + 关键帧编辑器(#5)

**理由**:P1/P2 做出了能出片的管线,但**镜头语言只有三种固定模式**,非专业用户很难编排出好看的成片。方案 V2.1 的验收标准写的是「≥4 套模板可按段落组合;非专业用户 10 分钟内完成一条百公里赛道的镜头编排」——这条从未达成。

相机路径已按里程参数化,模板本质上是预置的关键帧生成器,基础设施是现成的。

### P3-D 自包含交互网页导出(#6)

**理由**:方案定位「视频负责引流,交互页负责深度查看,两者互补构成传播闭环」。现在闭环缺一半。

### P3-E 传感器覆盖度(#9)

**理由**:小而实在。FIT 里的 cadence/power/temp 现在被丢弃了;先入模型并做覆盖度概览,是后续任何分析的前提。

### 暂缓

- **#11 路网吸附**:数据源受阻,需先确认 Overpass 可达性或换源。**不在拿不到数据的情况下写路由引擎**——本项目已被两次"未经验证即交付"咬过。
- **#8 多活动对比 / #10 轨迹路网图层**:价值真实但依赖多轨迹管理体验,排在上述之后。
- **#12 TrackSource 适配器**:接口冻结的意义在于有第二个数据源要接;当前只有本地文件一种,先做等于空转。

## 三、`fit-ride-studio` 的可借鉴点(功能之外)

用户三次提到应参考其**视觉表现与菜单交互**。已确认可借鉴且尚未落地的:

1. **报告分区结构**:核心指标 / 坡度 / 主要爬坡 / 深度分析 / **行动建议** —— 前四项 P2 已实现,**「行动建议」未做**。这是把数据变成可执行结论的一步(例如"你在 60km 后配速衰减 23%,建议补给策略调整")。
2. **多画幅一致的视觉体系**:已在 P2 落地。
3. **对话式交互**:参考实现是 agent 驱动的,用户描述需求即可产出报告。本项目是 GUI 应用,**不照搬**,但其"少配置、直接出结果"的取向值得保留——速算模式已体现。

## 五、风险

| # | 风险 | 应对 |
|---|---|---|
| R-1 | ExcelJS 体积不小,可能拖累主包 | 走动态 `import()`,与 Cesium 同样处理 |
| R-2 | EXIF 含个人位置信息 | 全程本地解析,不上传;界面明示 |
| R-3 | 单文件交互网页需内嵌轨迹数据,长轨迹会很大 | 抽稀后嵌入,并提示体积;超限给出提示而非静默截断 |
| R-4 | 「行动建议」容易沦为套话 | 只在数据支持时给出结论,并附依据数值;宁可不给,不给空话 |
