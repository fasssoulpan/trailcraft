## 一、本阶段定位

P0 解决"读得准"(解析、坐标系、统计),P1 解决"看得见"(3D 巡游)。**P2 解决两件事:一是让实跑轨迹产出有价值的表现分析,二是把巡游从"预览级录屏"升级为"传播级成片"。**

用户需求原话:「判断如果是实跑轨迹,把 ITRA 表现分的逆向算法及功能也整合进来」,以及参考 fit-ride-studio 的「功能、视觉表现、菜单交互」。

### 1.1 与既有规划的关系

fit-ride-studio 的多项特性与方案 V2.1 已规划的 P2/P3 内容重合,可视为对既有方向的印证:

| fit-ride-studio 特性 | 方案 V2.1 对应 |
|---|---|
| 9:16 / 1:1 / 3:4 / 16:9 多画幅导出 | P2「竖屏 9:16 使用独立 HUD 排版」 |
| 照片按 GPS/时间戳匹配路线 | §5.1「挂载实景照片(自动读取 EXIF GPS 纠偏)」 |
| H.264 MP4 导出 | §三 选型「WebCodecs + mp4-muxer」 |
| 报告面板 / 深度分析 | §5.7「自包含交互网页」的近亲 |

**其额外带来的新思路**:爬坡段自动识别 + 坡度分布、照片故事视频、多活动对比、传感器覆盖度概览。

### 1.2 一个关键的选型收敛

方案 V2.1 的视频编码选型本就是 **WebCodecs + mp4-muxer(H.264)**;P1 的 `MediaRecorder`/WebM 只是标注为「预览级」的权宜实现。因此 P2 做确定性逐帧管线时,**天然产出 H.264 MP4**,与 fit-ride-studio 的 `H.264 MP4、30 FPS、12 Mbps` 规格自然对齐,不需要额外决策。国内传播场景(微信、视频号、小红书)对 MP4 的兼容性也显著优于 WebM,这条本身就是必要升级而非锦上添花。

## 三、技术设计

### 3.1 实跑 vs 规划轨迹的判别(交付物 1)

这是 ITRA 功能的前提:**只有实跑轨迹才有"表现"可言**,对一条规划路线算表现分毫无意义且会误导。

判别依据(按可靠性排序):

1. **时间戳存在且跨度合理** —— 规划轨迹通常无 `time` 列(P0 已实测:补充数据里两条 KML 路线均无时间列,两条 FIT 实跑均有);
2. **时间跨度与里程的比值落在人类运动速度区间** —— 排除"有时间戳但是等速合成"的情况;
3. **采样间隔的真实性** —— 设备记录的间隔有抖动,合成的等距时间戳则完全均匀;
4. **心率/步频等传感器列存在** —— 强证据(仅实跑有)。

判别结果为三态:`recorded`(实跑)/ `planned`(规划)/ `uncertain`,**不确定时不猜**,界面上让用户一键指定。判别逻辑放纯函数模块并单测——这是"能不能算表现分"的开关,错判的代价是给用户一个假分数。

### 3.2 表现分析引擎(交付物 2~4)

移植 `cyber-trail-hud/src/analysis/` 的核心算法,改写为 TypeScript 并适配 P0 的列式数据模型:

| 参考实现 | TrailCraft 落点 | 说明 |
|---|---|---|
| `scoring_v4.js` (214行) | `src/core/perf/score.ts` | 幂律模型 PI = min(1000, C×(kme_v2/hours)^K × envFactor);C=30.0, K=1.25 |
| `gap.js` (88行) | `src/core/perf/gap.ts` | 坡度修正配速,含 `isHikingSegment` 判别 |
| `elevation.js` 的 `calculateGradeSegments` | `src/core/perf/climbs.ts` | 坡度分段 → 爬坡段识别 |
| `env-compensation.js` (58行) | `src/core/perf/env.ts` | 海拔/温度环境补偿系数 |
| `splits.js` (85行) | `src/core/perf/splits.ts` | 公里分段 |

**移植原则**(与 P1 §5 一致):
- 保留 P0 列式 TypedArray,不引入参考实现的对象数组;
- 去除模块级可变状态;
- **数值行为必须与参考实现一致**,并以其为基准写回归测试——这是移植而非重写,算法本身已经过作者用真实数据校准(双锚点:平路 92km/186m 12.75h→PI≈366,UTMB 170km/10000m 20h→PI≈1000);
- km-effort 复用 P0 已验证的爬升统计(阈值滞回),而非参考实现自己的一套,避免同一工程里两个爬升数字。

**一处必须校准的差异**:参考实现的 `summary.totalAscent` 来自它自己的爬升算法;TrailCraft 用 P0 的阈值滞回算法(已用崇礼官方数据验证,误差 −4.8%)。移植时以 P0 的为准,并记录这会使 PI 相对参考实现有系统性偏移,需重新验证等级阈值。

### 3.3 表现报告面板(交付物 5)

借鉴 fit-ride-studio 的分区结构(核心指标 / 坡度 / 主要爬坡 / 深度分析),但**视觉语言沿用 TrailCraft 现有的深色面板体系**,不引入第二套设计语言。

面板仅在轨迹判别为 `recorded` 时可用;`planned` 轨迹显示的是既有的关门预警与分段表——这两者是互补的:**规划轨迹回答"我能不能按时完赛",实跑轨迹回答"我跑得怎么样"**。

菜单交互上,采纳参考实现的一个做法:报告作为可从主界面唤出的浮层,而非常驻侧栏——侧栏已经很拥挤(P1 期间已因此把模式切换改为固定吸顶)。

### 3.4 确定性逐帧渲染管线(交付物 6~8)

这是 P2 的技术主线,也是方案 V2.1 从一开始就要求的能力。

**为什么必须换掉录屏**:`MediaRecorder` 捕获的是实时渲染结果,机器性能波动直接变成掉帧,且分辨率受限于画布。方案 V2.1 原文:「必须采用与实时帧率解耦的确定性逐帧渲染管线」。

**实现路径**:
1. 渲染循环改由**固定步长的虚拟时间**驱动(每帧推进 1/30 或 1/60 秒),而非真实时钟;
2. 每帧:推进相机 → 等待 Cesium 完成该帧渲染(`scene.postRender` / `requestRender` 同步)→ 读取画布 → 与叠加层合成 → 送入编码器;
3. 编码走 **WebCodecs `VideoEncoder`** + `mp4-muxer`,而非 MediaRecorder;
4. 录制前沿相机路径**预取瓦片**,避免地形/影像未加载导致的空帧。

**P1 已经打好的基础**:相机路径按里程参数化(而非帧序号),这正是逐帧管线能复用同一路径的前提;叠加层合成器(N5)已能绘制到任意 Canvas 上下文与任意分辨率。

**多画幅**:竖屏 9:16 使用独立排版模板(HUD 元素重新布局),而非横屏裁切——参考实现同样是这个取舍。

**兜底**:超长任务(百公里巡游约 2 万帧)的内存压力,采用分段渲染分段编码、及时释放帧缓冲;必要时按方案 V2.1 的 R4 走 Electron + ffmpeg 路线。

## 四、里程碑

| 里程碑 | 内容 | 验收 |
|---|---|---|
| Q1 | 实跑/规划判别 + 判别结果驱动的界面分支 | 四条真实样本(2 FIT 实跑 / 2 KML 规划)判别 100% 正确 |
| Q2 | 表现分析引擎移植(评分、GAP、爬坡识别、环境补偿) | 与参考实现在同输入下结果一致;纯函数全单测 |
| Q3 | 表现报告面板 | 数值与 P0 统计模块一致;仅实跑轨迹可用 |
| Q4 | 确定性逐帧渲染管线 + WebCodecs/MP4 | 两台机器导出逐帧一致(SSIM > 0.99);10 分钟 4K 在 16GB 机器完成 |
| Q5 | 多画幅与合规片尾 + P2 验收 | 四种画幅正确输出;竖屏独立排版;署名清单核对通过 |

每个里程碑:TDD(可测部分)→ 自测 → 代码评审 → commit + tag(`p2-q1`…`p2-q5`,完成打 `v0.3.0`)。

**验收纪律**(P1 教训):涉及渲染的功能,必须由真人在真实浏览器确认后才算完成。P1 期间有一个从项目第一天就存在的 MapLibre Worker 缺陷,因为开发沙箱不合成帧而长期未被发现——数据层验证再充分也替代不了真人看一眼。

## 五、许可与合规

- `fit-ride-studio` 为 **AGPL-3.0**。本项目**不复制其代码**,仅借鉴功能划分、报告分区与交互取舍(思想不受版权保护)。若未来需要直接引用其代码,必须先评估 AGPL 传染性对本项目发布方式的影响。
- `cyber-trail-hud` 为用户自有项目,算法移植无许可障碍,但移植后应在代码注释中标注出处。
- ITRA 表现分为**社区逆向估算**,非 ITRA 官方认证分数。界面必须明确标注这一点,避免用户误以为是官方成绩——这是产品诚信问题,不是免责话术。

## 六、风险

| # | 风险 | 应对 |
|---|---|---|
| R1 | 表现分算法与 ITRA 官方口径存在差异,用户据此产生误判 | 界面明示为社区估算;展示计算依据(km-effort、用时)让用户自行判断 |
| R2 | 移植后因爬升算法不同导致等级阈值失准 | 用真实轨迹重新校准阈值;保留"无修正版"分数便于横向比较 |
| R3 | WebCodecs 在部分浏览器/硬件不可用 | 运行时探测编码器能力;降级 VP9/WebM;文档标注推荐 Chromium |
| R4 | 4K 逐帧渲染的内存与时长压力 | 分段渲染分段编码;及时释放帧缓冲;Electron+ffmpeg 兜底 |
| R5 | 判别实跑/规划出错,给规划路线算出表现分 | 三态判别,不确定时不猜、交用户指定;判别逻辑单测覆盖 |
