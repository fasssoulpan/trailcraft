## 三、P2 表现分模型的当前状态与推理

### 3.1 参数

`src/core/perf/score.ts`:`PI = min(1000, C × (kme/hours)^K × (kme/270)^M × envFactor)`,`C=77.9, K=0.850, M=0.155`。

`M/K = 0.182` → 隐含 Riegel 耐力指数 **1.18**,落在超长距离越野的经验区间(1.10~1.20)内。

等级阈值:精英级 680 / 优秀 500 / 良好 380 / 中等 200 / 入门 <200。

### 3.2 走过的弯路(避免重蹈)

1. **原始移植**(`C=30, K=1.25, 无距离项`):短距离严重高估——13.9km 训练跑得 1000 封顶,404km 活动仅 298。
2. **加距离项后过度矫正**(`M=0.295`):隐含"10 倍距离慢 63%",远超 Riegel 的 13~29%,导致短距离被压得过低。
3. **发现虚假数据点**:崇礼 70km 组那行的爬升是按 168km 组比例估算的,算出均速 15.5 km/h——比 UTMB/OCC 冠军在同类地形上都快,不可能。这一个点绑架了整个拟合,一度让**赢 UTMB 得 808 分而赢区域性 70km 得 954 分**。
4. **现状**:崇礼 100/70/50km 三行全部排除出拟合与结构检查(仅存档并记录剔除理由),M 受 Riegel 约束重新拟合。

### 3.3 数据可信度分级(`src/core/perf/calibration.ts`)

- **可核实**:参考实现的平地锚点;2025 UTMB 周赛事(赛道规格来自 `race-presets.js`,成绩来自 iRunFar);崇礼 168km(规格来自赛事自带 KML);本项目 12 条真实轨迹(仅用于结构单调性检查)
- **已排除**:崇礼 100/70/50km(爬升为估算,70km 行物理上不可能)
- **仍是假设**:"国际精英落在 900~960 区间"是我根据其实力的推断,**没有任何一位选手的官方单场 ITRA 分数**

### 3.4 关于分段拟合的判断

用户提议过分段拟合。**当前不该做**:可核实的数值锚点只剩一个,其余全是结构约束;在这种数据量下增加分段只会拟合噪声。**需要的是更多真实数据,不是更多参数。**

### 3.5 最能提升准确度的数据(如能拿到)

1. 2025 UTMB 周赛事、崇礼各组的**官方单场 ITRA 得分**
2. 崇礼 100/70/50km 组的**实测赛道规格**(GPX/KML)
3. 2025 OCC 备用赛道的实际距离爬升
4. **中段完赛者**数据,不要只有冠军

## 五、已知限制

- 视频录制:若降级到 MediaRecorder 则仍是预览级(WebM),UI 会如实标注
- 表现分:社区逆向估算,**非官方 ITRA 积分**,界面已明示;绝对刻度建立在 §3.3 的假设上
- KMZ 不支持;拼接不支持拖拽排序;`splitAt` 后 CP 全部重锚到前半段
- 规划模式(MapLibre)无等高线——该模式未加载高程数据
- 坐标偏转为社区公开近似实现,国内商业发布前需做测绘法规合规评估
- **仍缺样本**:国内 App(两步路/六只脚等)导出的 GCJ-02 轨迹——P0 验收标准 2 因此仍标"部分"
