## 二、实测验证过的关键结论

- **解析性能**:330,062 点 / 105MB 的 GPX 解析 1.14 秒(验收要求"1万点 < 2秒")。正则快路径不建 XML 树是关键。
- **距离算法可信**:10 条真实 COROS 轨迹与设备自报里程逐条对比,偏差稳定在 0.8%~3.2% 且方向一致。
- **免费地形链跑通**:浏览器实测角标显示「地形:Esri · 影像:Esri」,无需任何 Key,未用 Cesium ion。
- **数据链路一致性**:巡游进度条拖到 100% 时 HUD 累计爬升 781m,与直接从原始文件按阈值 5m 计算的结果分毫不差,证明 HUD 前缀和与 `computeGainLoss` 一致(P1 验收标准第 6 条)。
- **雷达下一站计算**:待爬升 240m / 279m 与分段统计的各段爬升完全一致;剩余里程与各 CP 里程精确吻合。
- **底图切换**:署名在 Esri/Maxar 与 OpenStreetMap 间正确切换,96 个 Esri 瓦片请求确实发出,反复切换轨迹图层不丢失。
- **可达性实测(2026-08-07,经代理,不代表真实国内直连)**:Esri 地形 200/1.10s;Esri 影像 200/2.30s;天地图超时;OSM 200/3.37s。

## 四、已做的设计决策(供追溯)

- **距离雷达语义**:原方案 §3.7 留了"同心距离圈 vs 距下一个CP指示器"的悬念,用户授权自行决定。最终**两者合一,以下一站信息为主**:距离圈提供尺度参照,CP 作为光点标在环上,下一站高亮并配主文字读数(名称/剩余里程/待爬升/关门时间)。理由:只有距离圈的雷达等于把尺子画成圆,而选手真正要问的是"下一个补给站还有多远、还要爬多少"。
- **保留 P0 数据层**:P1 未采用参考实现的对象数组模型。33 万点场景下列式 TypedArray 内存开销约为其 1/5~1/10,且 P0 全部统计模块依赖列式。
- **相机按里程参数化**而非帧序号:倍速变化不改变路径,且 P2 逐帧渲染可复用同一路径。
- **叠加层走独立 DOM/Canvas** 而非画进 Cesium 场景:不受相机俯仰影响、便于竖屏独立排版;代价是录制需额外合成(已在 N5 解决)。

## 六、已知限制与遗留

- 录制为预览级(见 §五)。
- KMZ 不支持,提示用户解压后导入 `doc.kml`。
- 轨迹拼接按列表当前顺序,不支持拖拽排序;`joinTracks` 仅在所选首条为活动轨迹时解析正确。
- `splitAt` 后全部 CP 重锚定到前半段,后半段的 CP 需人工复核。
- 规划模式(MapLibre)无等高线——该模式未加载高程数据,UI 中已禁用并说明。
- 坐标偏转为社区公开近似实现,国内商业发布前需做测绘法规合规评估。
- **仍缺测试样本**:真实 FIT 文件、KML 文件、国内平台(两步路/六只脚等)导出的 GCJ-02 轨迹各若干;以及任一测试轨迹对应赛事的官方总爬升数值(用于验证 ≤8% 误差指标)。
