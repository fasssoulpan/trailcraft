## 三、缺口与后续动作

以下三项非功能缺陷,均需用户补充测试数据后复测:

1. **FIT / KML 真实样本为零**。当前 `测试` 目录仅有 GPX。FIT 解析器的纯函数部分(`recordsToTrack`)已单测覆盖,但 `parseFit` 对 `fit-file-parser` 的集成路径未经真实文件验证;KML 解析器仅经合成用例验证。
   → **需要**:手表导出的 `.fit` 文件、两步路/六只脚导出的 `.kml` 文件各若干。

2. **坐标系识别率无法测量**。识别率 ≥95% 的指标需要 GCJ-02 来源样本;现有 10 条全部是 COROS 设备的 WGS-84 轨迹,识别 10/10 正确但样本单一。
   → **需要**:两步路 / 六只脚 / 行者 / 奥维等国内 App 导出的轨迹文件。

3. **爬升误差 ≤8% 未对照官方数据**。`calibrateThreshold`(3~10m 网格搜索对齐官方总爬升)已实现并单测,但没有任一测试轨迹对应的赛事官方爬升数值可比对。测试文件多为超长多日记录(最长 404 km / 142 小时),并非单场比赛。
   → **需要**:任一条轨迹对应赛事的官方公布总爬升数值。

## 四、已知限制(设计取舍,非缺陷)

- **底图**:使用 OSM 官方栅格瓦片,国内访问不稳定。瓦片 URL 已抽为常量便于替换;瓦片加载失败时应用会提示「底图瓦片加载失败,轨迹功能不受影响」,轨迹、剖面、CP 等全部功能不依赖底图。
- **KMZ**:不支持,导入时提示用户解压后导入 `doc.kml`。
- **拼接**:按轨迹列表当前顺序拼接,不支持拖拽排序;`joinTracks` 的活动轨迹解析仅在所选首条为活动轨迹时正确。
- **分割后的 CP 归属**:`splitAt` 产生两条轨迹,现全部 CP 重锚定到保留在原位置的前半段(·A),属于后半段的 CP 需人工复核。
- **关门时间时区**:`datetime-local` 输入按浏览器当前时区补写偏移量,跨时区编辑同一工程需注意。
- **坐标偏转合规**:GCJ-02/BD-09 转换为社区公开近似实现。方案 V2.1 已列明:面向国内商业发布前需完成测绘相关法规合规评估。

## 五、开发过程中修复的重要缺陷

浏览器验收与代码评审共发现并修复以下问题,均已提交:

| 缺陷 | 影响 | 提交 |
|------|------|------|
| 地图就绪判断用 `isStyleLoaded()`,依赖底图瓦片加载完成 | 国内瓦片不通时,轨迹图层、自动缩放、悬停标记全部静默失效 | `7b28aaf` |
| `Marker.addTo()` 先于 `setLngLat()` | maplibre v6 下必抛异常,悬停标记根本无法显示 | `7b28aaf` |
| 工具箱操作后 CP 不重锚定 | 抽稀后 `anchorIndex` 越界(如 200000 → 仅剩数千点) | `a5153a9` |
| 工具箱操作后 `activeTrackId` 被清空 | 连续操作断链 | `a5153a9` |
| 海拔正则不支持科学计数法 | 整列海拔被静默丢弃(非单点 NaN) | `cea603e` |
| `locateByDist` 在单点数组返回 −1 | 下游读取 undefined,静默传播 NaN | `8f4f1a9` |
| BD-09 转换缺 `outOfChina` 判断 | 境外坐标被错误偏移 600~900m | `525d76b` |
| 识别正则无词边界 | 如 "Snapple" 误匹配 "apple",高置信度下静默套用错误坐标系 | `cf54a2e` |
| FIT 无时间戳时产生全 NaN 列而非 undefined | 违反"整列缺失→undefined"约定 | `27889e2` |
