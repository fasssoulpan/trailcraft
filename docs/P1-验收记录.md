## 三、N5 视频录制 —— 本环境的验证边界

milestone N5(本次里程碑,视频录制)是**唯一一项其核心功能本身依赖渲染帧**的交付物:`MediaRecorder`/`canvas.captureStream()` 录制的就是"每一帧实际画出来的像素",而本环境 `requestAnimationFrame` 从不触发,Cesium 从未渲染过一帧,因此:

- **录制出的 WebM 文件内容**(是否有画面、HUD/CP 卡片/雷达是否正确合成进画面、分辨率是否为 1080p)—— 无法在本环境验证;
- **录制自动从头开始、播放到终点自动停止** —— 依赖 `FlythroughEngine` 的 `onTick`(由 `viewer.clock.onTick` 驱动,同样依赖渲染帧)—— 无法在本环境验证;
- **暂停/恢复录制不冻结画面**(`requestRenderMode` 协调逻辑,见 `cesium/recorder.ts` 文件注释)—— 该逻辑的正确性依赖观察连续渲染的帧,无法在本环境验证。

已在本环境完成、与渲染无关的验证:

- `npx tsc -b --force` 零错误(strict 模式);
- 纯逻辑单测:`overlay/captureLayout.ts`(布局数学)、`overlay/frameCompositor.ts#compositeFrame`(帧合成顺序)、`overlay/captureDraw.ts`(画布绘制调用,使用假 ctx)、`hudStats.ts#formatHudStats`、`checkpointApproach.ts#buildCheckpointCardData`/`formatCheckpointCutoff` —— 全部通过;
- 构建产物确认 `recorder.ts` 及其依赖停留在懒加载 chunk,未进入主包。

**用户需在自己的机器(真实 Chrome/Edge)上确认的清单**:

1. 点击「录制视频」后,巡游是否从里程 0 开始播放;
2. 录制期间画面是否持续更新(而不是冻结),尤其是**手动点击暂停**之后录制是否仍在继续写入帧(这正是 `requestRenderMode` 协调逻辑要防止的失败模式);
3. 播放到终点时录制是否自动停止并触发下载;
4. 下载的 `.webm` 文件用播放器打开,画面中是否**同时包含** Cesium 3D 场景与 HUD 数值、(如有)接近中的 CP 卡片、(如启用)距离雷达 —— 这是本里程碑要解决的 R8 风险的最终验证;
5. 分辨率是否为 1920×1080;
6. 控制台报告的编码(VP9/VP8/WebM,`FlyControls` 录制行文案会显示)是否符合预期;
7. 在不支持 `MediaRecorder`/`canvas.captureStream` 的浏览器打开时,是否显示明确提示而不是白屏或报错。

## 四、缺口与后续动作

1. **距离雷达的语义已确认**(方案 §3.7 遗留的开放问题,现已由用户裁定):同心距离圈与"距下一个 CP 的距离指示器"二者都要,不是二选一——同心圈保留作为比例尺参考,下一检查点(名称、沿途剩余距离、剩余爬升、关门时间)作为主要读数。理由:纯粹的同心圈只回答"这个抽象距离有多远"这类比较空的问题,而一名越野跑者预览路线时真正想知道的是"下一个补给站/打卡点还有多远、还要爬多少",方案本身也把关门时间分析定位为"选手赛前功课的核心刚需"——因此雷达上必须有"目标",不能只是一把画成圆圈的尺子。已实现:`overlay/radarTargets.ts`(纯函数、无 Cesium/React/Canvas 依赖,给出每个检查点相对相机朝向的方位角与直线距离、是否已通过、以及下一个检查点的沿途剩余距离/剩余爬升——爬升复用 `buildRunningGain` 前缀和与 HUD 共享的 `hudStats.ts` 缓存,不重复扫描全轨迹;单测覆盖开关机点选取、沿途/直线距离在之字形轨迹上的真实差异、方位角环绕 360° 等边界情形)+ `overlay/radarRender.ts`(在雷达扫描面上把检查点画成目标点,下一个目标放大加环并带引导线,以及独立的下一检查点文字读数面板,随画布高度自适应字号)+ `overlay/captureDraw.ts`/`cesium/recorder.ts`(录制画面同步合成,不会出现"录像里雷达信息比屏幕上少"的情况)。视觉呈现(读数是否清晰、目标点定位是否符合直觉)仍需用户在真实浏览器中确认,见本环境的结构性限制说明。
2. **距离雷达圆心的潜在不一致**:`RadarOverlay.tsx`(N6 既有代码,本次未修改)把 `projectRadarCenter` 返回的、相对于**整个 Cesium 画布**的屏幕坐标,直接当作圆心传给一个固定停靠在右下角、仅 150×150px 的小画布。如果这两个坐标系之间确实没有做偏移换算,雷达在正常运动点位置(通常接近画面中央)时可能整体绘制到这个小画布范围之外,导致雷达看似"空白"。本次 N5 为录制合成实现的雷达(`overlay/captureDraw.ts#drawRadarCapture`)刻意采用"雷达在自己的方框内自我居中"(只用运动点位置换算出的 `metersPerPixel`/朝向,不用其绝对屏幕坐标)—— 这是一个独立、经过推理确认自洽的实现,但**没有去改动/验证 N6 原有的屏幕雷达**,因为超出本里程碑范围。建议用户在真实浏览器中确认巡游模式下屏幕右下角的雷达是否可见、居中是否正确;如确认存在此问题,应作为独立缺陷修复,而不是在 N5 顺带处理。
3. **底图切换（3D 侧）、等高线可读性、CP 卡片动画、相机三模式** —— 均已实现且有单测覆盖纯逻辑部分,但视觉效果本身需要用户在真实浏览器中确认(见第一节表格逐项说明)。

## 五、已知限制(设计取舍,非缺陷)

- **预览级录制**(P1 §1.4/R4):`MediaRecorder` 是实时抓取,慢帧(大地形瓦片到达、GC 停顿)在输出里就是真实丢帧,分辨率也受限于"能实时编码"这个约束,而非场景本身的渲染上限。`FlyControls` 的录制按钮旁始终显示「预览级 1080p 实时录屏」文案(不仅录制中才显示),避免用户把这次输出当作最终画质天花板。4K/竖屏/确定性逐帧渲染管线是 P2 工作;相机路径已按里程(而非帧序号)参数化,为 P2 复用做好了准备。
- **在线地形依赖**(P1 §6 R1):与"本地优先、离线可用"的原则冲突,国内直连可达性仍需真实网络复测。
- **等高线间距分档与雷达量程档位**:纯数学部分(`contourSpacing.ts`/`radarMath.ts`)均已单测,但两者的最终视觉可读性(尤其是等高线在卫星图与平面图两种底图上是否都清晰)未在真实浏览器中确认。
- **距离雷达语义**:已确认为"同心圈 + 下一检查点指示器"二者兼具,详见"四、缺口"第 1 条;视觉呈现仍待用户在真实浏览器中复核。
